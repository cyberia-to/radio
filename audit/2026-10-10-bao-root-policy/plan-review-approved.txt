## 1. B1 (memory-store producer closure) — resolved, verified

Traced end-to-end in the now-supplied `store/mem.rs`:

- `import_bytes` → `PreOrderMemOutboard::create(&data, IROH_BLOCK_SIZE)`; `ImportEntry.outboard`.
- `Actor::finish_import` keys by `import_data.outboard.root()` (the `Outboard` impl returns the `root` field) → `get_or_create_entry(hash)`, then `CompleteStorage::new(data, outboard.data)`.
- `import_byte_stream` and non-wasm `import_path` both terminate in `import_bytes(res.into(), scope, format, tx)`. The wasm `import_path` errors out. No independent derivation.
- `CompleteStorage::create(data)` → `PreOrderMemOutboard::create` → `outboard.root()`; `readonly_mem::ReadonlyMemStore::new` is its only non-test caller.
- `PreOrderMemOutboard::create` → `io::outboard::outboard` → private `outboard.rs::hash_block` (reduction #2). So both memory stores inherit `hash_group`.
- `import_bao` / `BaoFileStorage::Partial` retain the **caller-supplied** request hash (`ImportBaoRequest{hash,size}` → `get_or_create_entry`) and complete via `CompleteStorage::new`, not `create` — no whole-body key derivation. Research's statement is accurate.

`PostOrderMemOutboard::create` also routes through the same `outboard()` and is cross-checked by the existing `post_order_outboard_all_nodes_match_pre_order` root assertion; it carries no reduction of its own, so its omission from step 2 is harmless.

The planned tests are decisive at an affected length: `D`=8192 at log4 → `chunks=2, cpb=16, blocks=1`, so `ReadonlyMemStore::new([D])` exercises `CompleteStorage::create` and `MemStore::add_bytes(D)` exercises `import_bytes`/`finish_import`. `list().hashes()` is race-free: `finish_import` inserts into `state.data` *before* sending `Done(tt)`, and `with_tag`'s `CreateTag` is a later round-trip to the same actor. `export_bao(key, ranges(0,2)).bao_to_vec()` is exactly `LE64(8192)||D` (8200 B): `pre_order_chunks_filtered` with `blocks==1` emits one `Leaf{0, min(8192,65536)=8192, is_root:true}` after `leaf_range 0..16` overlaps `0..2`; `into_byte_stream` maps `Size`→8 LE bytes, `Leaf`→data, `Done`→end. `get_bytes` returns `D`. `mem.rs::smoke` (65536 B — itself inside the affected interval) survives: every value is derived from the new key, and `blocks==1` means `import_bao` sees no `Parent`.

## 3. Independent canon and boundary re-derivation

`specs/tree.md` §Root Finalization and `rs/src/tree.rs::{fixed_chunk_root, merge_range}` agree: single chunk → `hash_leaf(d,0,true)` (CHUNK|ROOT); multi-chunk → `hash_node(l,r,true)` (PARENT|ROOT); interiors non-ROOT; leaf counter is the **absolute** chunk index; `split = largest power of two < count`. CDC `root_hash` is correctly excluded, with `tree.4k_zeros` forbidden for the right reason (`root_hash_uniform_4096_splits_at_2048`).

All five reductions are behaviourally identical today, including `sync::hash_subtree` (its `len<=CHUNK_LEN` shortcut equals the others' empty/single-chunk returns because `is_single_chunk = len<=CHUNK_SIZE && is_root`); consolidation is exactly behaviour-preserving modulo the one flag. `is_root && level.len()==2` identifies the final iteration precisely, since `next.len()=ceil(len/2)==1 ⟺ len==2` under `while len>1`; I hand-checked bottom-up-with-promotion against `merge_range` for n=3,5,7 and group composition for 4+2/4+3/16+1. For `blocks>1` the root node `npot(blocks)-1` always has an existing right child, so the ROOT `Parent` is always emitted and never inherited down to a leaf — no internal group can be ROOT-finalized, and multi-group roots are unchanged. Affected iff `4096 < N <= 4096·2^g`: log4 4097..65536, log2 4097..16384 ✓. Published anchors hold pre- and post-fix (`Hash::new(b"")=ea57b2e6…`, `Hash::new(b"hello")=626fa46e…` via `tree_hash` → `blocks<=1` → `chunk_cv(·,0,true)`).

Error/event pins all check out: combined `decode::DecodeError::LeafMismatch{start_chunk:0}`; `SliceDecodeError::LeafMismatch{start_chunk:0}` (the `blocks<=1` branch); `sync::EncodeError::LeafHashMismatch(ChunkNum(0))`; FSM `io::error::DecodeError::LeafHashMismatch(ChunkNum(0))`; mixed = `Size(8192)`, `Error(LeafHashMismatch(ChunkNum(0)))`, `Ok(())` with no `Parent`/`Leaf`/`Done` (the `Leaf` arm returns before any `send`), canonical = `Size(8192)`, `Leaf{offset:0,data:D}`, `Done`, `Ok(())`. `BlobTicket::{to,from}_bytes` pass the hash through unchanged ✓. Privacy is fine: a private `hash_group` in `io/mod.rs` is visible to `io::{outboard,decode,slice,sync}` as descendants; keeping `let _ = block_bytes;` in the public wrapper avoids an `unused_variables` error under `-Dwarnings` while preserving the documented parameter name. A recording backend is implementable within `HashBackend`'s bounds (`AsRef<[u8]> + Clone + Eq + Debug`); `hash_group` touches only `chunk_hash`/`parent_hash`. PR32's 131072 B fixture (`9ccd2809…`/`108022aa…`) is unaffected and its `half_root`+single-ROOT shape is already post-fix.

## 4. Decision on the deliberate behavioural identity change

**Accept, as scoped.** It is mandated by pinned primary authority and restores the property `specs/tree.md` states explicitly: a file's identity must never equal an internal chaining value. Today an 8192-byte log4 root *is* `parent_cv(chunk_cv(d0,0,false), chunk_cv(d1,1,false), false)` — an internal CV of any larger file sharing that prefix at the same absolute counters. Conditions, all already in the plan and required in the receipt: source-level `semver-checks` green certifies **nothing** about content identity and must be stated as such; no alias/dual-acceptance (it would re-admit the collision this removes); old references become unresolvable rather than silently wrong (`readonly_mem::export_bao` builds its outboard from the *requested* hash, so a corrected provider returns `LeafHashMismatch` instead of serving an old-keyed body; old tickets still parse but name an unservable root); recovery needs the complete body plus rebuilt references, as partial affected-length records have an empty outboard and no retained root provenance; no deployment inventory exists; rollback is asymmetric. Version/tag/release consequences belong to the release train as a recorded compatibility note, not to this patch.

## 6. Existing defects to record (not caused by, not in scope of, this patch)

1. **`mem.rs::import_bao` panics on any `Parent`**: `pair[..64].copy_from_slice(parent.pair.0.as_bytes())` copies 32 bytes into a 64-byte slice. Latent only because every current test uses single-group data (`smoke` = 65536 B = 1 block). Same old-width class as PR32; `print_outboard` (128/64 strides) shares it. Now citable from the pack.
2. `Hash::EMPTY = [0u8;32]` is not the real empty root (`ea57b2e6…`): `observe_with_opts` short-circuits on it, `import_bao_reader` accepts a zero-size body only for it, and `MemStore` keeps a phantom `empty_hash` handle while a genuine `add_bytes(b"")` indexes under the canonical root. `hash.rs::test_empty_hash` pins only determinism.
3. Two distinct public `DecodeError` types (`io::error` vs `io::decode`) with the same name; the plan distinguishes them per path correctly.
4. `slice::decode_slice`'s `blocks<=1` branch ignores `ranges` and `declared_size`, folding trailing bytes into the leaf; `decode::decode` checks size only after the walk.
5. `sync::valid_ranges` granularity inconsistency (per-file vs per-block) inside a touched function.
6. `sync::encode_ranges_validated` panics (`load(*node)?.unwrap()`, `stack.pop().unwrap()`) where `mixed.rs` returns `EncodeError` for the same conditions.
7. `BaoTree::blocks()` is `.max(1)`, so the `blocks == 0` branches in `tree.rs` and `sync::validate_ranges_impl` are dead.
8. `radio-integration-tests` links registry `cyber-hemera 0.1.2` alongside path `0.3.1` via `cyber-bao` — two `Hash` types in one crate; the planned `-p radio-integration-tests` gate inherits it.

Carried baseline reds from both 2026-10-09 receipts: cyber-bao Clippy (first `io/mixed.rs:115 clone_on_copy`), workspace `Endpoint`/`PublicKey` local-vs-registry mismatches and `iroh/bench` imports, format drift, `v0.1.0` lock unresolvable under `--locked`, unavailable nextest/deny/`nightly-2025-10-09`.
