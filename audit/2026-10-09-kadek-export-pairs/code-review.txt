## Production correctness

**`encode_parent_pair` (`iroh-blobs/src/api/blobs.rs`, module-level private fn above `impl ExportBaoProgress`)**

```rust
let mut data = [0; 2 * hemera::OUTPUT_BYTES];
let (left, right) = data.split_at_mut(hemera::OUTPUT_BYTES);
left.copy_from_slice(pair.0.as_bytes());
right.copy_from_slice(pair.1.as_bytes());
```

Correct and width-derived, not width-hardcoded. The array type is fixed by the return annotation; both halves are exactly `OUTPUT_BYTES`, so each `copy_from_slice` is length-matched by construction — the exact failure mode the baseline exhibited. Order is `left || right`, matching the consumer: `cyber-bao/src/io/slice.rs::decode_slice` reads `left_bytes = &slice[cursor..cursor+hash_size]`, `right_bytes = &slice[cursor+hash_size..cursor+pair_size]` with `pair_size = backend.hash_size()*2`, and `cyber-bao/src/tree.rs` sizes the outboard with `PAIR_SIZE = OUTPUT_BYTES*2`. The exporter is now consistent with the decoder rather than with a 128-byte phantom layout.

**Three integrations.** All three parent arms are reduced to one call, and nothing else in the arms changed:

- `write`: `target.write(&data)` — `&[u8; 64]` coerces to `&[u8]`; byte count on the wire is 64.
- `write_with_progress`: `writer.send(&data).await?;` **then** `progress.log_other_write(data.len())`. Credit is 64, is derived from the buffer rather than a literal, and is reached only after a successful send — so a failed or partially-accepted parent write credits nothing. This is the precise 128→64 accounting defect, fixed in the right order.
- `into_byte_stream`: `Bytes::copy_from_slice(&data)` yields a 64-byte chunk; the previous `vec![0u8;128].into()` padding is gone.

`EncodedItem::Size` still emits `size.to_le_bytes()` (LE64) and credits 8; leaf arms, `Done`/`Error` arms, and the `?`-based error mapping (`io::Error` → `ExportBaoError::ExportBaoIo`, `EncodeError` → `ExportBaoInner`, `ProgressError` → `ClientError`, per `api.rs`) are untouched. `data_to_bytes`/`data_to_vec` still ignore parents. Scope is exactly: one private fn, three call sites, one `#[cfg(test)] mod export_pairs;` declaration. No public API, hash domain, root, storage, manifest or lock change — consistent with the semver run reporting 202 pass / 58 skip, "no semver update required".

**Regression risk from the change itself is structurally bounded**: the baseline arms panicked *unconditionally* on any `Parent` (confirmed by `logs/red-debug.stdout` at `blobs.rs:1122`, `:1154`, `:1181`), so no previously-green test could have depended on the 128-byte width. This fix can only unbreak parent-bearing paths — which materially reduces the exposure created by the unfinished broad unit suites.

## Independent oracle: geometry and root

`support.rs::geometry()` pins `CHUNK_SIZE == 4096` and `IROH_BLOCK_SIZE.bytes() == 65536` with distinct messages, then derives `C = 16`. Checked against source: `tree.rs` gives `CHUNK_SIZE: usize = 4096`, `from_chunk_log(log) -> Self(log)`, `bytes() -> CHUNK_SIZE << self.0`, and `store/mod.rs` selects `from_chunk_log(4)` ⇒ 65536. So body `2*B = 131072` = 32 chunks = 2 blocks, query `ChunkNum(16)..ChunkNum(32)` = exactly the right block ⇒ one `Parent` plus the right `Leaf`, and `8 + 2*32 + 65536 = 65608` with overhead `8 + 64 = 72`. Every number in the tests follows from the pinned constants.

`right_fixture()` is genuinely independent of radio's traversal: 32 `chunk_cv(bytes, i, false)` with absolute counters, each 16-leaf half reduced by four explicit `parent_cv(..., false)` levels in `half_root`, then `root = parent_cv(left, right, true)`, and the wire assembled by hand as `LE64 || left || right || data[B..]`. Two independent facts are then checked at once: (a) the store accepts that root at all — it must match `CompleteStorage::create`'s `PreOrderMemOutboard` root or `export_bao` would take the `None` arm in `readonly_mem.rs` and fail with `UnexpectedEof`; (b) all three exporter methods reproduce the hand-assembled bytes. The `decode_slice` cross-check is sound for this shape: `pre_order_chunks_filtered` emits `Parent { is_root: true, left: false, right: true }` for the root, pushes only `right_hash`, and `hash_block_for_verify` reduces 16 chunk CVs (counters 16..32, `is_single_chunk == false`) through the same 16→8→4→2→1 `parent_hash(..., false)` ladder as `half_root` — so the expected `[(65536, data[65536..])]` is right, not an accidental agreement.

The parent-free control is also correct: 4096 bytes ⇒ `blocks() == 1`, `outboard_size() == 0`, single root leaf, `chunk_cv(data, 0, true)` as root, wire `LE64(4096) || data`, overhead 8, no `Parent`. Together with `readonly_store_missing` and `geometry_pins` these are the three baseline passes (`3 passed; 8 failed`), which is exactly the control/trigger split a red-first unit should show.
