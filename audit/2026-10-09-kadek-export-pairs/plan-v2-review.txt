## Correction 1 — chunk geometry: confirmed, numbers check out

`tree.rs` supplies `pub const CHUNK_SIZE: usize = 4096;`, `from_chunk_log(log) -> Self(log)` and `bytes(self) -> CHUNK_SIZE << self.0`. With `store/mod.rs`'s `from_chunk_log(4)`:

- B = `4096 << 4` = **65536** (the `2^4*1024 = 16KiB` comment is stale by 4×; research correctly records it as stale and excludes repair).
- C = B/CHUNK_SIZE = **16**; body `2*B` = **131072** = 32 chunks = 2 blocks; query `ChunkNum(16)..ChunkNum(32)` = exactly the right block ⇒ **one** Parent, right Leaf at offset 65536 length 65536.
- Wire `8 + 2*32 + 65536` = **65608**; overhead `8 + 64` = **72**. Every number in the plan's table is consistent with the supplied constants.

The oracle shape is also right for this geometry: 32 leaf CVs with absolute counters and `root=false`, each 16-leaf half reduced through exactly four pairwise levels (16→8→4→2→1) with `root=false`, then `root = parent_cv(L,R,true)`. Deriving B/C/body/query from the constants while *separately* pinning CHUNK_SIZE=4096 and B=65536 with distinct messages is the right structure — a geometry change fails on its own named assertion instead of masquerading as the width bug.

Parent-free control is now correct too: `BaoTree::new(4096, from_chunk_log(4))` ⇒ `chunks()=1`, `blocks()=1`, `pre_order_chunks()` yields a single `Leaf { start_chunk: 0, size: 4096, is_root: true }` and `outboard_size()=0` — no Parent, and `len <= CHUNK_SIZE && is_root` makes `chunk_cv(data,0,true)` the correct independent root. This is the one shape that avoids the grouped-single-root discrepancy, as asked.
